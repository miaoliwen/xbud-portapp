# K-TRUTH：k 字段真伪与 K 来源判定（2026-11-14）

> 承接 `docs/ENVELOPE-NEXT.md` 与 `analysis/workdirs/out_so/REPORT.md`。
> 本轮全部结论**实测**（真机 MuMu 192.168.3.39，pid 55372/47687/49444），有脚本与原始日志可复现。
> 一句话：**k 字段的内容服务端根本不用于恢复会话密钥——我们用自生成 RSA 公钥替换了 app 的内嵌公钥，
> 服务端照样解密、照样受理提交（rrid 落库确认）。K 不在 k 里、不在内存裸存、不在 .so 明文里——
> 它是 native 从稳定材料派生的，唯一剩余取法 = 逆向派生函数本身。**

## 1. 决定性实验：伪造公钥替换（SPKI hijack）

### 1.1 方法

libnetseckit-4.2.4.so 的 .data 段内嵌一把 RSA-1024 SPKI 公钥（vaddr `0x181990`，file `0x171990`，162B，
REPORT §4.1）。它全库仅被 `0x38960` 处一条虚调用引用（`0x38950` 块：`x2 = SPKI, w3 = 162`，
旁路还有 16B 常量 `0x181270 = 9d7cd71971fb9a985a32bded8a20786a` 一并传入）。

PC 侧纯标准库生成一对新的 RSA-1024（`_mem/forged_key.txt`：n/e/d/p/q），构造同格式 162B SPKI
（`_mem/forged_spki.bin`），按 nespatch 同款 `/proc/pid/mem` 手法替换：

1. **进程内存级**（对运行中 pid 直接写 .data 页）：内存读回成功，但**服务端行为无变化**——
   ENC 后 DEC 照常、间隔与对照窗口一致 → 说明 SPKI 是 **init 时一次性解析**成内部大数对象，
   事后改 .data 的 DER blob 不影响已解析的密钥。
2. **文件级**（改 `/data/app/.../lib/arm64/libnetseckit-4.2.4.so` 的 `0x171990` 162B + 重启 app）：
   新进程 init 时解析到的是**我们的公钥**。从此该进程发出的所有信封的 `k` 字段都是
   **用我们的公钥加密的**——我们有私钥，可以逐字节还原 k 的 RSA 明文。

### 1.2 结果

- 伪造 so 下重启的进程（pid 49444）里，LSPosed 模块（`diag=1`）记录了 **24 条完整信封**
  （ret 未截断，k 完整 172 b64），全部用我们的私钥成功解密 → 24 组 128B RSA 明文。
- **明文形态**：128B 全随机、逐请求不同、无 PKCS#1 v1.5 结构（首字节非 00）、两两 XOR 零位为 0、
  每字节位置熵近满 → **既无填充结构也无任何跨请求常量区**。
- **服务端行为**：`4K.OK`（提交成功，uuid=4bf3c646…，rrid=72238810）+ `4K.CONFIRM IN_STORAGE`
  （二次拉列表确认记录在库）+ 每条 ENC 后 DEC 正常返回。
  **这些信封的 k 是服务端私钥解不开的**（我们公钥 ≠ 服务端公钥），服务端却照常解密 d、照常受理。
- 实验后 so 文件已恢复原样（sha256 `2ac02258…c4081` 与 REPORT 记录的原始值一致），cfg 已复位 enabled=0。

### 1.3 结论（E13）

| 判定 | 依据 |
|---|---|
| **k 的内容不参与服务端会话密钥恢复** | 伪造公钥下服务端照常受理（4K.OK/CONFIRM） |
| k 不是 K 的传输通道 | 24 组 RSA 明文全随机、无常量区；若 K 在其中（无论何种固定布局）必现常量字节 |
| k 最可能是：长度/格式校验 + 审计/抗篡改字段 | 服务端仅需 `len(b64decode(k))==128`（或更宽松）即可走通 |
| **K 由 native 从稳定材料派生**（或服务端同源派生） | K 进程内恒定（E5）；不在 .so/内存/k/响应里裸存 |

### 1.4 对产品路线的直接冲击

- **M1 的"k 封装点"阻塞解除**：PC 侧伪造信封时 k 可填**任意 128B**（建议先发一条探针确认服务端
  是否校验 k 为合法 base64/长度，预期通过）。原"定位 RSA 封装点+复现封装"的工作项**作废**。
- **M0 收窄**：剩余唯一阻塞 = **K（与 IV、h）的客户端来源**。三个候选来源按证据排序：
  1. native 派生：`K = f(稳定材料)`（token/deviceId/0x181270 常量/…）——服务端同源可算。
     证据：K 进程内恒定；不在任何存储里裸存；伪造 k 不影响服务端认知的 K。
  2. 首次下发 + 双端缓存：首请求 k 真实封装过 K，服务端按会话缓存。与"伪造 k 全程受理"矛盾
     （新进程 49444 从第一条请求起 k 就是垃圾，服务端仍解得开 d）→ **基本排除**。
  3. 纯设备指纹派生（与登录无关）：待验证。
- **h**：仍需 K（或等价密钥材料）才能闭合。拿到 K 后按 Path 3 穷举。

## 3. 修正后的协议模型（2026-11-14 版）

```
请求  {"d": b64(SM4-CBC(K, IV, [变长头][b64(body)])),
       "h": 32hex(K,明文 的某确定性函数, 待闭合),
       "k": b64(RSA-1024(128B 随机材料)),      ← 内容服务端不用（E13）
       "p": "101", "t": "0"}
响应  {"r": b64(SM4-CBC(K', IV', b64(JSON))), "s": 128B, "v": 101}
```

- K/IV：进程内恒定；来源 = native 派生（非传输、非存储、非 .so 常量）。
- `k`：客户端 RSA 装饰字段，**任意 128B 可过**（待最终探针确认校验强度）。
- `d` 明文的头部（旧文档称"177B prologue"）：**实测长度随进程/请求变化**
  （pid 55372 的 {"page":1} 信封 d=208B → 头≈168-176B；pid 49444 同 body d=88B → 头≈40-56B）
  ——旧"固定 177B"模型作废，头部是会话/设备态的变长结构，其内容仍是解密后才能看到的对象。

## 4. 下一步（按性价比）

1. **k 校验强度探针**（分钟级）：PC 直发一条 `k=固定128B` 的自造信封（d/h 用采集的 K——见 3；
   若 K 未得，先重放一条完整旧信封改 k 字段），判据沿用 200+0B vs 业务响应。
2. **K 派生逆向**（唯一硬阻塞）：目标函数 = libnetseckit 内 `0x39030`（SM4 key schedule）的调用方
   上文（`0x95bcc` 所在大函数）与 `0x38960` SPKI 解析函数所在状态机；重点线索：
   `0x181270` 16B 常量（与 SPKI 同一调用传入，疑似 KDF 种子）。
   静态路线：Ghidra/IDA 反汇编 arm64 so（翻译执行不影响静态分析）；动态路线：真机 arm64 环境下
   Frida 可 hook（MuMu x86 不行）。
3. **K 稳定性测绘**（闭合产品形态）：同 token 下重启 app → 用「服务端受理」为 K-相等 oracle：
   PC 重放一条旧 (d,h,k) 信封（同 K 才会被服务端解密成功）→ 受理 = K 跨进程不变 → K 每安装/每登录
   固定 → 设备只需一次 K 供给；不受理 = K 每进程轮换 → 密钥代理形态（现状架构已覆盖）。
4. **h 闭合**（拿到 K 后一天内）：24 组 (K, 明文, d, h) 同进程样本已就位（`_mem/mats.pkl`），
   按 Path 3 构造空间穷举即可定死。

### 6.1 K 生成器已完整定位（静态）

| 环节 | 地址 | 内容 |
|---|---|---|
| 信封加密核心 | `0x95374-0x9607c`（eh_frame 边界） | per-request 入口：vfunc25 取 key → SM4 key schedule(`0x39030`) → CBC(`0x17d00`) |
| **密钥生成器 vfunc25** | `0x97d08` | `srand(time(NULL))` + `rand()%N` 从解码字母表取 16 个可打印字符 |
| 字母表 | 118B 混淆表 @栈 | `(b^0x4f)+0x52 <0x80 ? +0x52 : -0x2d` 解码 → **87 字符**：`0-9a-zA-Z` + `` ` ~ @ # $ % ^ & * ( ) - _ = + \ | [ ] { } ; : '`` |
| RNG 实现 | GOT 符号表直证 | slot 0x140=`srand` / 0x148=`rand` / 0x158=`time` —— **libc 原生 rand**（bionic TYPE_3） |
| 加工函数 | `0x4c234-0x4cf1c`（3.2KB） | 随机串 + 65B 常量(`0x139ac0`) + 上下文 → 真 SM4 key；**此变换是最后缺口** |

### 6.2 服务端判定升级（E14/E15）

- **E14【实测】**：对 55372 会话（01:30）与 49444 会话（02:45，伪造 k）的信封做**首次重放**
  （k 原样），服务端均返回 **200+349B 确定性加密响应**（两次重放 r 逐字节一致）；
  相同 d 换 k（全零/顺序字节/短 k/非 b64/去 k）→ **200+0B 全拒**。
  注意：变体与 orig 的 d 相同，存在重放保护混淆，k 的确切校验规则未定——但
  **PC 侧用内嵌公钥 PKCS1v15 包任意内容即与 app 的 k 形态一致**（此前 forge-probe 的失败是 h/K，不是 k）。
- **E15【实测】**：app **完整重启（新 srand 种子）后**重放，两个不同会话的信封依旧过
  → **K 跨进程、跨数小时不变 = 每登录固定** → vfunc25 的 srand(time) 是**登录时刻**的一次性生成，
  K 随 token 存续；客户端每进程从持久层恢复或同源重算。

### 6.3 种子暴力结果（E16）

`seedbrute.c`（bionic TYPE_3 random + 字母表 + SM4 验证）扫 **1790500000-1794700000
（2026-10-03 → 11-14，420 万秒）**：0 命中 → **裸 16 字符 ≠ SM4 key**，`0x4c234` 变换必经。
同时冻结 dump（SIGSTOP@首条 ENC 后 73ms，scudo/Mem/bss/stack 217MB）+ keyhunt4（d 末块结构验证，
穷举 padlen，全量解密复核）0 命中 → 变换后的 key 也不以 16B 裸窗存在，或栈帧已回收。

### 6.4 通往完全脱离的最后一步

**逆向 `0x4c234`**（有界任务）：
1. 输入：vfunc25 的 16 随机字符（x2）、65B 常量 `0x139ac0`、上下文对象；
2. 输出：SM4 key（写入 keybuf，`0x95bcc` 消费）；
3. 内部调用 `0xef924`、`0xec7a4`（带 `0x181a48` 常量）疑似 SM3/KDF；
4. 逆向完成后：K = transform(gen(seed))，seedbrute 秒级出 K → **d/h/k 全离线可造 → 完全脱离**。

备用锚点：`getSecretKey(4)` 的 33 字符 salt（`2slhe02lsfiwowlcixisla_sls-_slaor`）若与生成器同源，
可作为 transform/RNG 实现的离线自测向量（长度 33 vs 16，同字母表）。

### 7.3 keybuf 纯度证明 + 架构判定（E17）

- x26（keybuf=[x29+0x268]）在 0x95374 内**只赋值一次、零改写**（grep 全量核对）；
  0x4c234 只读它 → key schedule 消费的 = vfunc25 的裸输出

  → 当前进程的请求路径**根本不经过 0x95374/keybuf**
- **判定（E17）：`0x95374` 是登录期一次性函数**（生成会话密钥 + SM2 协商 + 写 k 字段），
  日常请求用**缓存的对象内变换形态密钥**——这同时解释：E15 跨进程稳定、冻结抓不到、
  brute 失败（K=transform(字符,SM2材料) 非裸字符）

天然通过边界+熵过滤）。真正的 vfunc25 keybuf 从未在任何快照中以字母表形态出现。

**h-as-key 排除**：h(32hex)=16B 直接当 key / ASCII 截取 / md5/sha256 派生 / 换 IV，全部解不开 d。

**0x4c234 定式（静态钉死）**：输出 = `[65B 常量块][16B XOR(chars, SM2 材料拼接)][32B 附加]`
≈97-113B = **k 字段的 RSA 明文组装器**。16 随机字符只进入 k 的装饰位——而 k 服务端不读
（E13+E18）→ **16 随机字符对会话密钥无贡献**，任务书"K = transform(gen(seed))"的输入侧
前提不成立。

**0xef924 重判**：变参函数（va_list 布局）= 日志/printf 包装，非 SM3/KDF。

**裁定（E19）**：login d 的加密密钥在**入口/中段/返回/DEC 全部冻结点位**（累计 11+ 快照、
~8GB、keyhunt4 BE-rk / keyhunt6 LE-rk（s5-s9 含 515 文件收尾段全 0）/ keyhunt7 精确明文对 三引擎）均无裸 16B key 或
连续 128B 轮密钥。唯一自洽解释 = **0x39030/0x17d00 并非标准 SM4**，而是白盒化实现
（key schedule 内嵌混淆，明文 key 从不落内存；k/chars/SM2 材料 = 白盒表派生的输入）。
GB/T 向量自测过的是我方实现，非库方实现——库的 CBC 输入/输出布局同样未经明文验证
（快照中从未出现 [header][b64(body)] 连续缓冲，b64(body) 与 d 密文片段均 0 命中）。

**设备卫生**：libnetseckit 已复原原版（sha256 2ac02258…c4081 核对一致），lgarm* 旗标清理，
app 原版 so 下重启运行正常。

### 10.2 日常加密路径（0x93aa0）的实际结构

```
0x93aa0(obj, env, jstring)
  0x93cb4  vtable+0xc8 = 0x97d08    → K0 = 16 个随机字符（srand(time)+rand()%87）
  0x93cc4  obj+0x30 子对象 vtable+0x18 = 0x348b8
           args = (subobj, K0, 16, out1, &len, mode=0xb)
  0x348b8  → 0xf823c（EVP 式密码调度，输出 0x400 缓冲；k 的封装/变换在此）
  后续     → SM4-CBC（0x39bb8 的另一份内联 key schedule）→ 信封
```

- `0x348b8` 的参数校验是 `len==16 && key!=NULL && out!=NULL && mode<=0xc`；
  它先按 mode 构造算法对象（`[subobj]->[0x40]`），再走 `0xf823c` 的通用密码路径。
- 因此 **日常请求的 K0 也是每请求新生成的**（`srand(time)`），与上一轮 `0x95374` 的生成器同一套。
- 真实下发的 `k` 字段恒 128B；`k` 的 128B 明文/密文按 RSA 私钥解出来“全随机、无 PKCS#1 结构”
  （E13），与“`k` 不是 RSA 密文”完全一致——它更可能是 **SM2/EVP 密文（112B）+ 16B 头/填充**。
  内嵌的 64 hex `0x139ac0` 与 SM2 曲线参数（`0x139c70/0x139c28`）支持这条通道。
  → E13 的“k 内容服务端不用”应改判为“**k 的 RSA 层不是 K 通道；K 通道在 SM2/EVP 层**”。

- 盐：5 个 getSecretKey + 0x181270 的 16B 常量 `9d7cd71971fb9a985a32bded8a20786a`
- 编码：16B 摘要的 hex 大小写；长摘要取前/后 16B 的 hex

K 来源：`--k-hex` / `--k-ascii` / `--seed N` / `--seed-range A-B`；
`--seed` 用上面的 94 字母表 + 设备同款 bionic TYPE_3 `random()` 生成 K0。

**首轮判定（负结果，但把缺口钉死）**

1. 对 16:27:09 的 3 组同秒样本，`--seed-range 1794644824-1794644836`（13 个 K0）：
   `partial_rule_hits=0, FULL=none`。
2. 直接用这 13 个 K0 解对应真实 d（IV=0 / d[:16] / d[16:32] 三种布局，
   在明文里搜 raw body 与 b64(body)，**不假设 padding**）：全部 0 命中。

→ **日常 CBC 的 key 不是裸 K0**；`0x348b8` 变换的输出才是 K1。
→ h 的碰撞器已就位，但必须先用 K1 运行：`python crack_h.py --k-hex <K1>`。

### 10.8 K1 的下一步取法（已定位到具体点位）

真实 ENC 路径在 emulator 里已能走到变换入口：

```
0x93cb4  vfunc25 → K0（16B，x1=keybuf）
0x348b8  transform(subobj, K0, 16, out1, &len, mode=0xb)
```

`0x348b8` 内部按 mode=0xb 构造算法对象（`vtable 0x17cd90 +0x40 = 0x352e0` 的 0xb 分支），
再调 `0xf823c`（EVP 式调度）。仿真环境里 `0xf823c` 返回 `9`，变换走失败分支
（真实设备上该环境由 JNI 上下文/证书/Provider 提供）。

两条取 K1 的路线：

- **设备侧同帧冻结**：把 `0x93cf4`（变换返回后的判断点）改成 `b .`，进程会停在
  K0/K1 都还在栈上的瞬间；随后 dump 可写内存，用 keyhunt 以同帧明文/密文验证 K1。
  这是最直接的路线，且不依赖仿真环境的 Provider。
- **补仿真 Provider**：定位并只执行初始化 0x180d50/0x180eb8 的 `.init_array` 构造器，
  使 mode 0xb 的算法对象完整，再让 `0xf823c` 走通；之后同一 trace 可直接读 K1 与 h。

## 11. 第八轮（同日 18:00-18:15）：协议全闭合 —— AES-128-CBC + md5(P)，只剩 k

### 11.1 决定性反转：日常信封不是 SM4

用设备侧同帧冻结抓到 `0x93cf4` 的 keybuf，并与日志时间戳的 K0 逐字节对上后，
直接用它解 d 仍失败；把候选算法扩到 AES 后命中：

```
AES-128-CBC, key = K0(16 字符 ASCII), IV = 0, PKCS7
```

明文 P（实测）：

```json
{"data":"<b64(body)>
","keyDataFour":"...","keyDataOne":"...",
 "keyDataThree":"...","keyDataTwo":"...","platform":2,"timeStamp":<epoch秒>}
```

- `K0 = alphabet[rand()%94] x16`，`srand(epoch秒)`；字母表 94 字符（§10.6）。
- `h = md5(P)`（小写 hex，32 字符）——19/19 组实测全中。
- 请求头 `headerSign` 同一套：明文是身份/设备 JSON 的 b64 包装，AES+md5 相同。
- `keyData*` 为进程级常量（同一进程跨秒不变，重启进程改变）。

### 11.2 服务端 oracle 与 k 的地位

| 实验 | 结果 | 结论 |
|---|---|---|
| 官方 header+body 原样重放 | 200 + 349B | 信封受理 |
| header 或 body 的 k 换随机 128B | 200 + 0B | k 被服务端校验 |
| **自造 header+body + 借官方 k** | **200 + 349B** | 明文/字段/AES/md5/tokenSign 全对，唯一缺口 = k |
| body 之间互换 k（同会话） | 200 + 349B | body 的 k 可复用 |
| header 的 k 用于 body | 200 + 0B | k 有角色/会话作用域 |

“自造 + 借 k”成功那条是关键：除 k 以外，协议已经 100% 可离线生成。

### 11.3 k 的排除项（全部实测）

- 不是 `RSA-PKCS1v15(K0)`：自造 k 被 200+0B。
- 不是标准 SM2：官方 k 的前 64B 当 C1 点，19/19 不在 SM2 曲线上；
  自造标准 SM2（奇偶 × 顺序 × 明文布局）全部 200+0B。
- 不是响应 `s`：7 个请求 k 与 14 个响应 s 交叉无匹配。
- 伪造 SPKI 后用自己的私钥解 k：128B 无结构随机值，无 K0/时间戳/nonce/token/
  md5(P)/HMAC(token,P) 等任何常量或摘要。
- 结论（当前最佳）：**k 是服务端下发的会话级 128B 票据**；客户端每请求换新，
  服务端按会话/角色校验。E13 的“k 内容服务端不用”作废——k 必须有效。

## 13. 第十轮（同日 18:35-18:45）：响应解密闭合 — native envelope，不是同实例

### 13.1 决定性实验

| 请求信封 | 响应解密结果 |
|---|---|
| PROBE 取 k，PC 自造 header+body | HTTP 200 + 3141B；DECRYPT 返回 `{"error":-10000,"message":"ERROR"}` |
| PROBE 直接生成 headerSign 与 body（`encryptStringToServer(header_json)` / `(body_json)`） | HTTP 200 + 3141B；DECRYPT 返回业务 JSON（`error:10000`，记录列表） |
| app 自己发出的请求响应，事后用模块新建的 `SecruityInfo` 解 | 成功 |
| 同一响应重复 DECRYPT；带 body k / header k / 无 k / 伪造 k | native 是否认得响应与 Java 实例无关 |

### 13.2 原因

`SecruityInfo` 构造器拿的是进程单例：`c.a(context)` → `c.b()` →
`com.netease.NetSecKit.a.a.a` → `com.netease.NetSecKit.factory.a` →
`JNIFactory.getInstance()`。新建 `SecruityInfo` 不会新建 native 会话。
响应解密需要的是 native 在**生成该请求信封时**留下的会话态；只借 k、PC 自造 d/h，
native 没有对应的响应密钥，所以响应必然解不开。

因此：
- “按 k 缓存实例”不是杠杆；缓存本身已加（m74），但不会改变自造信封的响应解密结果。
- 正确做法：headerSign 和 body 都由 PROBE 直接生成，PC 只组装 HTTP；
  响应再经 DECRYPT 回到同一进程。

### 13.3 m74/m75

- PROBE/DECRYPT 支持 `input_b64`（任意 UTF-8 文本，绕开 adb shell 引号）。
- PROBE 按 k 缓存实例（LRU 32）；DECRYPT 支持 `--es k`，命中则复用，未命中新建；
  无 k 用最近一次 PROBE 的实例。
- `PROBE-CACHE / DECPROBE-USE / DECPROBE-MISS / DECPROBE-NEW` 日志用于判定实例路径。
- m75 增加 `--es mode 1`：走 `decryptStringFromServer(str, 1)`；get_config 返回空串，
  说明该端点不走 1 号通道。
- 构建：`deploy/build/build_probe.ps1` → `deploy/module/harness-nsk.apk`，versionName m75。

### 16.2 关键发现：0xf823c 的“失败分支”其实是 fopen 桩造成的

上一轮 §10.8 记录“仿真里 0xf823c 返回 9，变换走失败分支”。本轮定位到根因：

- `0xf823c` 内部两次 `fopen`，路径/模式字符串在 so 里为
  `0x146c90 = "/dev/urandom"`、`0x13e160 = "rb"`；
- 旧仿真器没有 fopen 桩 → 返回 0 → `0xf823c` 返回 `9`；
- `0x93cf4 cbz w0` 命中 → 走 `0x93d58` 提前返回，第二次变换与后续续段全部跳过。

补最小 FILE* 桩（`fopen`→假句柄，`fread`→确定性 xorshift 字节，`fclose/fseek/…`→0）后：
`0xf823c` 返回 0，`0x93cf4` 不跳，`0x93d24` 第二次变换、`0x93db4` 续段、
`0x93f20` 的 16 次追加、`0x93dac` 收尾全部实测走到。**所谓“变换失败”是桩缺陷，不是库行为。**

### 16.3 路径修正：0x39bb8/0x17d00 不在 0x93aa0 链上

- `0x39bb8` 全库唯一调用点 = `0xe5434`；`0x17d00` 调用点 = `0x95be8` 与 `0xe5454`。
- `0x93aa0` 与 `0x20058` 的实测块序列里都没有这两个点。
- `0x20058` 在 `0x93aa0` 返回后只做 `[JNIEnv]+0x538`（NewStringUTF）把结果串转 jstring 再 `ret`。

→ 修正 §10.2 的假设“0x93aa0 后续 → SM4-CBC(0x39bb8) → 信封”：日常 ENC native
不经过该 CBC 腿；CBC/封装属于 `0xe53xx`（或 Java 层）的另一条路，需单独入口去追。

### 16.4 证据等级

- `Observed`：块序列/计数、K0/ARG/OUT/RET 快照、fopen 路径字符串、`0x39bb8/0x17d00` 的调用点。
- `Inferred`：`0x93f20` 16 次循环 = 把变换输出逐字节并入返回串；返回串的内容未解
  （`[x29+0x68]` 读回 `d0 01 00 03…`，该库的 string 类布局未定，不作结论）。

### 17.1 native ↔ Java 分派（静态表 + vtable 重定位，实测吻合）

| Java 层 | i | native | vtable 槽 | 目标 | 状态 |
|---|---|---|---|---|---|

### 17.2 0xe4e0c（i=1 解密）块级推进

自然路径（`--entry 20284`，0.3s / 4.8k 块）：

```
0xe4e0c → 0xe4eb0 字符串构造 → [obj+0x20] vtable0
        → JNI: FindClass("java/util/UUID") / randomUUID / toString
        → 0x449f8 解析门 → 返回 0 → 0xe4fe4 清理 → ret
```

- JNI 调用记录：`CallStaticObjectMethodV`(115) + `GetMethodID`(33) + `CallObjectMethodV`(35, toString)
  + `NewStringUTF`；**没有任何 GetStringUTFChars/GetStringChars**。
- 输入 jstring 在本路径里根本没被读；解析门吃的是设备上下文串（UUID 派生）。
- 放行实验：`--nop 0xe4fa8 --poke 0xe4fe0=14000058` 强制走 0xe5140，
  到 `0xe51c0` 后跳到空函数指针（块起点 0x0，700 万块后超时）＝ provider/上下文墙；
  `0xe5434`(key schedule)/`0xe5454`(CBC) 仍未执行。

### 17.3 0xe43fc（i=0 解密，日常路径）块级推进

自然路径（`--entry 204b0`，0.1s / 4.9k 块，真实响应 `r` 768B 与任意 b64 结果相同）：

```
0xe43fc → 0xe44d8 [obj+0x20] vtable0（同为 UUID 上下文）
        → 0x449f8 解析门返回 0 → 0xe4570 → 清理 → 0xe4688 ret
```

- 喂真实 `r`（`_devdata/native_env_resp.json`，768 字符）与喂 `{}` **块序列完全一致**，
  再次证明：解析门不读 jstring，读的是 native 自己通过 Java 上下文拼出来的设备串。
- 因此 **i=0 解密在纯仿真下也走不进解密主体**；这是环境依赖（Android 上下文），
  不是算法问题。设备侧才是这条路径的可行观测面。

### 17.4 结论与下一步

1. 请求侧：`0x93aa0` 全链可仿真（§16），是纯协议路线唯一需要的 native 段。
2. 响应侧：i=0 解密 `0xe43fc` 需要真实 Android 上下文（UUID/设备串），纯仿真不可达；
   但写路径以“响应非 0B”为受理判据，不必解响应 → 对协议路线不构成阻塞。
3. i=1 通道（0xe4e0c / 0x95374 / 0x39bb8 / 0x17d00）在本 app 未使用，优先级降为最低。
4. 若后续要解响应：设备侧 Xposed 在 `decryptStringFromServer(str)` 返回处自停
   （m66 手法），冻结帧取 `0xe43fc` 内的 key/IV；或在仿真里补 Android 上下文对象
   （UUID 串、包名、设备路径等）直到 `0x449f8` 返回非 0。
